# 059 采集缓冲首帧在满刻度 —— 是**启动瞬态**，另外查出一个测试脚本的**读法错误**

**状态**：**已结案**（2026-10-04）。RTL **无需改动**；改的是 `scripts/test_pdm_onboard.tcl`
的读法 + 本档的结论。**两个误判，第二个比第一个严重得多。**
**相关**：[027](027-*.md)（下游互谱/白化本来就去 DC）、`build/tb_dc_probe.v`

---

## 1. 症状

上板跑 `scripts/test_pdm_onboard.tcl`，第 5 项读出：

```
words 0..7 = 80008000 00000000 00000000 00004A3E 000000FF 00000200 00000000 00000000
```

第 0 个字 = `0x80008000`（两个通道都是 24 位最小值）。其余"基本是 0，只带小残差"。

## 2. 误判一：以为直流阻断会把它滤掉

脚本原文（也是我写的）写的是

> 位流恒 0 ⇒ CIC 恒 −满刻度 ⇒ **直流阻断把它滤掉** ⇒ 0

判据因此写成 `want 0x00000000`。**"会被滤掉"是推理不是实测** ——
`build/tb_dc_probe.v` 单独量 `rv32_chan_align` 打脸：恒定输入 −8388608 下，
阻断确实收敛到 0，但**要 ~6000 个样点（≈150 ms）**：

```
样点 2000 → -168175    样点 4000 → -3120    样点 6000 起 → 0
```

⇒ **"收敛到 0"不等于"立刻是 0"**。而采集 bank 恰恰是**刚使能那一刻**采的。

## 3. 误判二（更严重）：step 5 根本没在读数据

规格 P-11 写明采集窗口是 **INDEX + DATA 两个寄存器**：

> 写 `INDEX` = 0..LEN·(N_CH/2)−1，再读 `DATA` 取那一个字。

而 step 5 写的是 `reg(0x20 + i*4)` —— 把窗口**当数组、递增地址**读 8 个"数据字"。
按寄存器表，那 8 个地址里**只有第 0 个是 DATA**：

| 脚本读到的地址 | 实际寄存器 | 那次实测值 | 说明 |
|---|---|---|---|
| `0x320` | `DATA` | `80008000` | ← **唯一一个真数据** |
| `0x324` | `ACKSEQ` | `00000000` | |
| `0x328` | `RELEASE` | `00000000` | |
| `0x32C` | `FRAME` | `00004A3E` = **19006** | 帧计数 |
| `0x330` | `FROZEN` | `000000FF` | 与单独读 `0x30` 一致 |
| `0x334` | `META` | `00000200` = **512** | = 默认 `LEN` |
| `0x338` / `0x33C` | 未用 | 0 | |

**六个全中，映射确认无疑。** 后果有两条：

1. **判据被带偏**：`words vary ⇒ 有真信号` 是**假的** —— 它们"在变"是因为
   读的是**不同的寄存器**，不是因为有信号。
2. **本档原来那句「`0x200` = 512 正好等于 `rv32_chan_align` 注释里的残差上界」
   是彻底的误读** —— `0x200` 是 `META` 寄存器，512 就是默认的 `LEN`，
   **与残差没有任何关系**。

> 教训：**"读出来的数看着合理"不是证据。** 一个 512 摆在"残差上界"的语境里
> 显得严丝合缝 —— 正是这种"太合适"最容易让人停止追问。
> 遇到一串多寄存器读数，**先逐条落到寄存器表上**再解读。
>
> ⚠ **而且这个巧合是真的**：`rv32_chan_align.v:35-38` 的注释确实写着
> 「恒定输入下残差最终停在 `[0, 2^DC_K)`，`DC_K=9` 时是 `[0, 512)`」——
> **512 真的是残差上界**。于是 `META` 读出来的 512 撞上了那个真值，
> 两边互相"印证"，误读变得**双重可信**。
> ⇒ **两个独立来源给出同一个数，只有当它们确实无关时才算独立证据。**
> 这里一个是寄存器快照、一个是算术性质，本来无关，但数值撞车掩盖了这一点。

## 4. 判决实验（`scripts/probe_pdm_firstword.tcl`）

用**正确的 INDEX+DATA 读法**，并且先做**寄存器表自证**（`META` 必须=512、
`FROZEN` 必须=0xFF —— 这两条不对就说明映射理解错了，后面的数据一概不能信）。

分两组：

- **A 组**：此刻躺在缓冲里的那一批（刚使能时采的）
- **B 组**：跑够 1.5 s 让阻断收敛后，**把两个 bank 都释放掉重采**

### 结果

**A 组**（`FIRST=1`，即采于帧 1，距今 1803.7 ms）：

```
frame 0: 80008000     frame 1: 80408040     frame 2: 807F807F  ...
         -32768               -32704               -32641
```

**一条从满刻度单调爬升的斜坡 —— 那就是直流阻断从初始状态收敛的轨迹本身。**
（每个"帧"占 4 个字 = 8 通道，通道间相同是因为输入恒定。）

**B 组**（`FIRST=174081`，采于 197.3 ms 前 —— 确认是**新采的**）：

```
data[0..11] = 00000000 00000000 00000000 ...
```

**全零。** 阻断收敛之后采下来就是 0，与设计一致。

> 旁证：A 组里 bank1 的 `FIRST=513`（采于使能后 ~13 ms），数据恒为 `0xD0F5` = −12043
> —— 正好是"阻断走到中途"的值。恒定输入 ⇒ 恒定输出，自洽。
>
> **附带的第二个收获**：B 组里 bank0 被成功重采（`FIRST` 1 → 174081），
> 但 **bank1 没有**（两次都是 513）。查 RTL —— **不是 bug，是握手在正常工作**：
> ```verilog
> wire release_ok = ... && selected_ready && ack_seq_q == selected_seq;
> ```
> 释放要求 PS **先 ACK 序号**。探针没写 `ACKSEQ`（`ack_seq_q` 停在复位值 0）：
> bank0 的 `seq0_q` 恰好是 0 ⇒ 撞上，放行；bank1 的 `seq1_q` ≠ 0 ⇒ **被正确拒绝**，
> 并计入 `ack_errors_q`。**设计拒绝了一个没走完握手的释放请求 —— 这正是它该做的。**
>
> **上一条当时是"推断"，现已实测确认。** 把 `test_pdm_onboard.tcl` 加了第 6 项，
> 按 P-11 的顺序（先写 `ACK_SEQ`，再 `RELEASE=1`）走完整握手：
> ```
> bank0 ACK_SEQ=0 -> RELEASE
> bank1 ACK_SEQ=1 -> RELEASE
> STATUS READY=3                       <- 两个 bank 都重采了
> bank0 (FIRST=89601)  bank1 (FIRST=94209)   <- 都从 1 / 513 前进了
> across both banks: 0/16 non-zero, 0 at full-scale
> ```
> **`ACK_SEQ` 实测就是 0 和 1**，与按 RTL 推的一致；走完握手后**两个 bank 都重采成功、
> 且都是全零**。⇒ 采集缓冲的**所有权握手在真硅上可用**，059 的结论对**两个 bank**
> 都成立，不只是 bank0。

## 5. 结论

**情形 (A) 启动瞬态。RTL 不需要改。**

`0x80008000` 是**真实且正确**的读数：它记录的是"链路刚起来、阻断还没收敛"那一刻
的真实状态。首帧是采集窗口的边界点，不进入后续处理（互谱/白化本来就去 DC，见 027）。

**改的是工具，不是设计**：

- `scripts/test_pdm_onboard.tcl` step 5 改成 INDEX+DATA 读法，并读 16 个字统计
  "几个满刻度 / 几个零"，不再用"地址递增"的假数组读法，也不再把 META 当残差。
- 新增 `scripts/probe_pdm_firstword.tcl`：带寄存器表自证的判决实验，可复用。

## 6. 复现指纹

- **上板读采集数据前先验寄存器表**：`META`=512、`FROZEN`=0xFF。两条不过 ⇒
  地址映射理解错了，**别解读数据**。
- **一串多寄存器读数里出现"看起来很合理"的数字**（比如 512 摆在一个讲残余的语境里）
  ⇒ 先落寄存器表。**"太合适"是最危险的信号。**
- **首帧满刻度 + 后面收敛** ⇒ 先问"这个 bank 是什么时候采的"，读 `R_FIRST`（0x314）
  与 `R_FRAME`（0x32C）作差；差小 ⇒ 刚采的，差大 ⇒ 是陈的。
  不要一上来改 RTL。
