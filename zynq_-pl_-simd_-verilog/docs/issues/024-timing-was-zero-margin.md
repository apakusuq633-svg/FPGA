# 024 关键路径本来就是零余量

**症状** 裸 PL 50 MHz：改动前 WNS = **+0.024 ns**，改动后 −1.436 ns。

**根因** 不是"改动破坏了时序"，而是**它本来就没有余量**。
两条路径分别是：

| | 9-20 | 9-21 |
|---|---|---|
| WNS | +0.024 ns | −1.436 ns |
| 失效端点 | 0 | 32 |
| 关键路径 | `u_ex_mem_reg` payload dff | **同一处** |

28 级逻辑、2 个 DSP48 + 12 个 CARRY4，而且**走线占了 21.4 ns 里的 10.6 ns（49%）** ——
一半是布线，说明是扇出/拥塞，不纯是逻辑深度。

**修法** 见 [023](../archive/issues/023-anc-coefficient-pipeline-timing.md)（ANC 那条已修）。裸 PL 这条另算 —— 它的源/目的都在
`u_ex_mem_reg` payload 上，28 级 + 49% 走线，得先看是不是拥塞导致的。

**复现/指纹** **"改了一点点就挂了"往往说明余量本来就接近 0。**
判据：把改动前后两次的 `Source:`/`Destination:` 拿来对 ——
**同一处**就是零余量被压过，**换了地方**才是引入了新路径。

## 附带教训：时序结论不能跨配置套用

| 配置 | 时钟 | 用途 |
|---|---|---|
| 裸 PL（`run_pl_bare.tcl`） | **50 MHz** | 台面探针，交付物走这条 |
| Zynq（`run_pl_flow.tcl`） | **40 MHz** | 产品配置，PS+PL |

两边的顶层、约束、时钟都不同，**一边的数字不能推另一边**。
而且第一轮跑错了方向：我拿裸 PL 的 −1.436 去怀疑 vec 单元，
真正的 8 ns 回归在 Zynq 那边、在 ANC 里。**先跑产品配置那条。**
