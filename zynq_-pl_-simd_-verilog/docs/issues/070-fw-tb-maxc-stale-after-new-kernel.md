# 070 — 加一个内核，四个**没碰过**的 TB 一起变红（MAXC 是陈旧口径）

**状态**：已修（2026-10-05）

---

## 症状

`tb_fw_das` 报：

```
4200000 拍，退休 3174828 条指令
FAIL: firmware must finish inside MAXC cycles
FAIL: firmware must set the done marker
DAS 一帧(512 样点 x 8 通道) = 843540 拍 = 205 拍/样点/通道
单麦基线 +0.25 dB  ->  DAS +6.74 dB  （改善 +6.49 dB）
```

注意**判据自己算出来的数是对的**（843,540 与台账一致），FAIL 的只是"没跑完"。

## 根因

`tb_fw_das.v` / `tb_fw_fft.v` / `tb_fw_gcc.v` / `tb_fw_srp.v` 四个 TB 的循环上限都是

```verilog
localparam integer MAXC = 4200000;   // 固件整轮 ≈ 270 万拍（FFT+GCC-PHAT+SRP+DAS）
```

**这四个 TB 都在等同一个"整轮结束"标记** `RES(15) == 0xC0DE0001`，
而 `fw_main.c` 是把 FFT/GCC/SRP/DAS/GSC **编进同一份固件**跑的（这是刻意的：
一份 `build`、一个 `.elf`，产品就是这么跑的）。

所以 GSC 一落地，整轮从 **3.35 M 涨到 11.2 M 拍**，
**这四个 TB 一行没改，就全部超时**。

## 误判（差点走错的路）

第一反应是"固件坏了 / 我刚改的倒数替换把 GSC 改死了"。**不是**：
- 判据打出来的 DAS 拍数、SNR 都是**正确值**，说明固件跑到那一步是好的
- 真正卡住的是**总拍数超过了 TB 的循环上限**

**分辨方法**：看 FAIL 的是"数值不对"还是"没跑完"。
`cyc == MAXC` 且判据里的数与台账一致 ⇒ 是**上限**问题，不是固件问题。

## 修法

四个 TB 的 `MAXC` 一律改成 **14000000**（1119 万 + 余量），注释写明当前整轮拍数。

⚠ **代价要认**：这四个 TB 现在都要真跑完 1119 万拍，单项从 ~4 分钟涨到 ~13 分钟，
`verify.ps1` 第 17 项从 ~15 分钟涨到约 **1 小时**。

**更好的修法（未做）**：让固件在各内核之后各设一个"段完成"标记，
TB 就可以只等到自己关心的那一段。**但这要占 `RES` 结果块的字**
—— 32 个字已经排满（DAS 21..28、GSC 29..31），**且 `.text` 只剩 28 B**。
所以先记着，等 §7 的阵列版 GSC 进来、标量版腾出空间时一起做。

## 复现指纹

```bash
# 现在的整轮拍数（实测，tb_fw_gsc 的 cyc）
vvp build/tb_fw_gsc.vvp | grep 拍
#   → 11,195,853 附近

# 陈旧上限的表现：cyc 恰好停在 MAXC，而判据里的数是正确的
vvp build/tb_fw_das.vvp | grep -E 'MAXC|DAS 一帧'
#   → "4200000 拍" + "DAS 一帧 = 843540 拍"（数对，但没跑完）
```

## 教训

**"TB 全绿"是个会自己失效的状态。** 只要判据依赖"跑完整轮"，
**任何新内核都会让不相干的 TB 变红**，而且它红的样子像"固件坏了"。

这类"共享总时长的判据"要么给足余量，要么改成**分段标记**。
本次先给余量（便宜），分段标记记在上面。
