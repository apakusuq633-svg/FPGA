# 028 「加密网格」不是证明 PL 必要性的有效旋钮

**状态**：已修（改的是论证口径，不是代码）
**日期**：2026-09-22
**阶段**：Stage 0（假设② 工作量清点）
**复现**：`scripts/golden/check_psonly.py`

---

## 症状

README §0.3 假设② 原来写的「不成立怎么办」是：

> §49 **Experiment 9** 就是这个折中：**加密网格**直到 PS 实时性崩掉、PL 撑住。

这条**从第一版就写进 README，但从来没有算过**。清点之后发现它是错的。

## 误判

**误以为 SRP 空间扫描是 PS-only 的负载大头。**

直觉上"1024 个网格点 × 28 对麦克风 = 28672 次累加"听起来就是最重的部分，
而且 README §25 整节都在讲 SIMD-MAC 怎么加速这个累加 —— 于是默认它就是瓶颈。

**错。** 精确清点（每帧操作数）：

| 块 | 每帧操作 | 占比 |
|---|---:|---:|
| **28×1024 点实数 IFFT** | 1,433,600 | **68.2%** |
| **8×1024 点实数 FFT** | 409,600 | **19.5%** |
| 28 对复数乘（互谱） | 86,184 | 4.1% |
| **SRP 扫描 1024×28** | **86,016** | **4.1%** |
| 28 对求模 \|G\| | 57,456 | 2.7% |
| 28 对倒数 | 28,728 | 1.4% |
| 峰值搜索 | 1,024 | 0.0% |
| **合计** | **2,102,608** | 100% |

**FFT + IFFT 占 87.7%，SRP 扫描只占 4.1%。**

于是「加密网格」这个旋钮：32×32 → 64×64 让 SRP 那 4.1% 涨 4 倍，
**总负载只涨 12.3%**。拿它去"把 PS 压垮"是压不垮的。

## 根因

**把"算法上最显眼的一步"当成了"计算上最重的一步"。**
README §25 花了整节讲 SRP 的 SIMD 映射，那是**处理器创新**的叙事需要，
不是**负载分析**的结论。两者被混为一谈了。

而真正的负载规律是：

- FFT/IFFT 次数 = 8 + 28 = 36 次/帧，每次 5·N·log₂N
- **28 次 IFFT 是因为麦克风对数是 C(N,2)，随通道数平方增长**
- SRP 扫描 = 网格数 × 对数，也随对数增长，但常数小得多

## 修法

### （1）换掉旋钮

真正能撬动负载的，按杠杆大小排：

| 旋钮 | 效果 | 代价 |
|---|---|---|
| **通道数** 8 → 16 | 对数 28 → 120（**4.3×**），FFT 8 → 16（2×） | 硬件重新做，README §4.2 明确说第一版不做 |
| **帧率** 76 → 更高 | 线性放大全部 | 需要理由（快速移动的声源），弱 |
| **NFFT** 1024 → 2048 | 每次 FFT 约 2.2× | 频率分辨率更好，但延迟翻倍 |
| ~~网格加密~~ | ~~+12%~~ | **无效，删掉** |

### （2）论证重心要挪

更根本的一条：**"PS 算不动"这个主张本身就不该是主轴。**

按 25% 的 NEON 有效率和 A9 @667 MHz 折：

```
浮点部分  11.4% / 0.25 = 45.5% CPU
定点部分   1.3% / 0.25 =  5.2% CPU
合计                    ≈ 51% CPU   （单核，未计 cache/DDR/中断）
```

而且帧率是可调的：**降到 25 fps（README §16 本来就说 20~50 Hz 足够），
负载直接降到约 52 Mop/s，A9 完全放得下。**

**所以诚实的口径是：**
- ❌ 「PS 算不出来」—— 站不住，降帧率就能算
- ✅ **「PS 算得出，但给不出确定性」** —— 这才是站得住的

后者正是 README §36 原本就写对的：

> PL 价值不能只看平均时间。PS-only 通常更容易受 cache、DDR、中断、OS 影响。
> PL 流水线强调 **deterministic latency**。

**所以 §34 的对照实验应该报的是 jitter 和 P95/P99，不是平均吞吐。**
平均吞吐上 PS 大概率不难看；难看的是尾延迟。

### （3）PL 侧的叙事也要跟着改

不能只吹"SRP 扫描被 SIMD-MAC 加速了"（那只是 4.1%）。
要落在**整条流水**：8 路 FFT + 互谱 + PHAT + 28 路 IFFT + 扫描，
其中 FFT/IFFT 那 87.7% 才是 SIMD-MAC 真正要吃下的量。

## 复现指纹

```bash
cd scripts/golden && python3 check_psonly.py
```

看那张占比表：`SRP 扫描 1024×28` 应该只有 **4.1%**，
而 `28×1024 点实数 IFFT` 是 **68.2%**。
把网格从 32×32 改成 64×64 再看总负载 —— 只涨一成。

## 留下的教训

- **论证不能凭直觉，要数** —— 这条 README §0 第一条就写了，这次违反的是它
- **"叙事上重要的模块" ≠ "负载上重要的模块"**：
  §25 讲 SIMD-MAC 与 SRP 的对应是为了**处理器创新**，
  但**负载分析**得出的结论是 FFT/IFFT 占 87.7%。两件事必须分开说。
- 这个坑**如果留到答辩**，评委会问「你把网格加密试试」，
  现场演示只涨 12%，很难看。**在 PC 上数一遍只花一秒。**
