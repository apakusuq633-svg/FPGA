# 087 VFFT 拆分段的中间和写在 16 位上下文里 ⇒ 与 C 的 int32 golden 不一致

**状态**：已修
**日期**：2026-10-07
**阶段**：逆变换（VFFT-inv）落地时顺手查出
**复现**：`tb/tb_fft_ifft.v`（满幅帧那一路）；语义最小复现见下

---

## 症状

**没有任何症状。** 这是这一条最该被记住的地方。

`tb_fft_bfly` 从 2026-09-22 起一直报 **513/513 条 bin 逐位一致**，
`test_acoustic_acceptance` 也一直报「VFFT 513 complex bins match independent golden」。
也就是说：**这个错从来没有被任何一条判据碰到过。**

只有当我把一个**满幅**的帧喂进去（`build/fft_frame_wide.hex`，±30000 加直流台阶），
`tb_fft_ifft` 才报出 **2/513 不符**，首条落在 bin 8：

```
首个不符: bin 8  实测 re=-20749 ... 期望 re=...
```

2/513 —— 如果把判据放宽成"大部分对"，它照样溜过去。

## 误判

没有误判的过程（是**读代码**时看出来的，不是查故障查出来的）：写反向拆分时
照着 `ifft512_real` 抄中间量，抄到 `wire signed [15:0] er = (zkr + zmr) >>> 1;`
这一行，旁边的注释还写着「中间量必须显式 32 位」。

先把 Verilog 的语义单独量了一遍（`build/tmp_sem/t.v`，iverilog）：

```
zkr = zmr = 30000
  16 位上下文 (zkr + zmr) >>> 1  →  -2768
  32 位上下文                    →  30000     ← C 给的是这个
```

**加法先溢出、再移位**，因为赋值目标的宽度（16）决定了整个右值表达式的上下文宽度。

## 根因

`rv32_fft_bfly.v` 的拆分段（ST_SPLIT）里八条中间量全部写成了 16 位上下文：

```verilog
wire signed [15:0] er  = ((zkr + zmr) >>> 1);   // 16 位上下文 ⇒ 先溢出再移位
...
wire signed [15:0] xr  = (er + str) >>> 1;      // 同理，而且 str 是 32 位，
                                                // 混进来会先被截到 16 位
wire [31:0] nyq_nx = {16'b0, ((er - orr) >>> 1)};
```

对应的 C 是 `const int32_t er = (pr + qr) >> 1;` —— **int32**。两边在
|zkr + zmr| > 32767 时就分道扬镳。

为什么一直没被发现：`zk/zr` 是 9 级蝶形之后的输出，幅度受输入帧限制。
固件那个帧是三角波 ±16384 加噪声 ±8192，实测两个操作数**从未同时越过 16384**。
所以这条错**在这里潜伏了很久，而且看起来完全正常**。

## 修法

把中间和显式扩到 32 位再运算，结果仍按 C 的 `(int16_t)` 语义截到低 16 位：

```verilog
wire signed [31:0] zkr32 = zkr, zki32 = zki, zmr32 = zmr, zmi32 = zmi;
wire signed [15:0] er  = ((zkr32 + zmr32) >>> 1);   // 32 位上下文
...
wire signed [31:0] xr_s = ({{16{er[15]}}, er} + str) >>> 1;
wire signed [15:0] xr  = xr_s[15:0];
```

同时补上 `tb_fft_ifft`：
- `scripts/golden/fw_ifft_host.c` 用**同一份 C 源码**在 host 上算 golden
  （满幅正变换、逆变换、满幅逆变换三组向量）；
- `tb/tb_fft_ifft.v` 拿硬件对这三组 golden 逐位比。

**判据有判别力这件事是量过的**：把改动回退成 16 位上下文，
`tb_fft_ifft` 立刻报 **2/513 不符**；改回来 **0/513**。

## 指纹

- **满幅输入下才错，中小幅度全对** —— 任何"用固件那个帧量一遍就收工"的判据
  都碰不到它。这与 [068](068-gsc-fixed-point-three-traps.md)、
  [082](082-verilog-shift-width-self-determined.md) 同族：
  **错的不是算法，是表达式在 Verilog 里的求值宽度。**
- 判据要够狠才有用：2/513 这种量级，必须**逐位比**、而且必须有一条
  "出错时会 FAIL"的负例（这里是满幅帧）。
- 通用规则：**Verilog 的赋值目标宽度就是右值表达式的上下文宽度。**
  与 C 对拍时，凡是 C 那边是 `int32_t` 的中间量，RTL 里都要显式扩位，
  不能靠"两边看起来一样长"。
