# 077　R 的行长绑死在 N_GRID ⇒ 小网格档位跨对读（静默算错）

**症状** 计划把 `rv32_srp_scan` 先按**固件同尺寸**（4 对 × 16×16）例化进 SoC，
好与固件金标准 `build/fw_srp_p.hex` 做跨实现逐位交叉验证。
读代码时发现：这个档位**根本不可能算对**，而且它已经写进了计划。

**误判** 原以为"先接小尺寸"只是少几个 BRAM tile 的事，逻辑一模一样。
实际上它不是"小一号"，而是**语义不同**。

**根因** LUT 与 R 的条数本来就不一样，但代码里都写成了 `N_GRID`：

- LUT 是**每格点**一条（`N_PAIR * N_GRID` 条）
- R 是**整条相关序列**（1024 = FFT_N 条），与网格点数无关

而 τ 绕回之后 `idx` 能取到 1000 以上（负延迟绕到序列尾部；固件那侧
一直是 `idx & 1023` 配 1024 长的 R）。R 的行只有 `N_GRID = 256` 深时，
`pair * 256 + 1013` 会落进**下一对的 R 行** —— 读到的每个值都合法、
不报错，只是**每一格都算错**。

**修法** 给 `rv32_srp_scan` 加 `R_LEN` 参数（**默认 = N_GRID，原行为逐位不变**），
只在 `r_mem` 尺寸与 `pair * R_LEN` 步长两处用它；`rv32_srp_regs` 透传它，
SoC 里例化传 `R_LEN=1024`。回归证据：`tb_srp_scan`（28×1024）改后**仍逐位 PASS**，
生成器默认档输出经 md5 比对**逐字节未变**。

**复现/指纹** 「一个模块里两个数组的长度写成了同一个参数」——
先问一句"它们真的同长吗"。这里不同长，而且**差的那部分正好落在地址绕回区间里**，
所以只在某些档位、某些延迟取值上错，大网格下永远不显形。

⚠ 与 [042](042-cic-comb-no-wraparound.md) / [068](068-gsc-fixed-point-three-traps.md) 同类：
**判据必须有能力失败** —— 只做大网格，这个 bug 一辈子不会出现。
