# 091 采样点的锁存时刻算错一拍（`TICK×25` vs `(TICK+1)×25`）

**症状** P-04 写的余量是「400 − 延时 − 100」，`rv32_pdm_clkgen.v` 的注释写
「`SAMPLE_TICK=4` → 低半周期正中，距前后两个沿各 100 ns」。按这个口径算，
tick 4 的建立余量看着很宽。拿 datasheet 的数一算，实际只有 **+16 ns**
（不到一个 40 MHz 拍），换麦、温度、更长的排线都会把它吃掉。

**误判** 一开始以为是「麦的推出延时比 P-04 假设的大」（P-04 假设 20–50 ns，
实际 `t_DV` max = 100 ns）。这个确实是**一半**的原因，但不是全部。

**根因** 还有**一拍**的换算错：

```
bit_en_o = en_i & (div_q[3:0] == SAMPLE_TICK)     // 组合，整个 tick 周期为高
```

`bit_en` 在整个 tick 周期里都是高，而**消费它的触发器在该周期结束的那个沿**才采样。
所以锁存时刻是 `(TICK+1)×25 ns`，不是 `TICK×25 ns`：

| tick | 距驱动沿 | **实际锁存** | 文档旧口径 |
|---|---|---|---|
| 4 | 100 ns | **125 ns** | 100 ns |

对 25 ns 的周期来说，这一拍就是余量的**三分之一** —— 正因为差了这一拍，
「tick 4 贴着边」这件事在旧文档里根本看不出来。

**修法**
- `pdm_decim.py` §8 把两个数**都打出来**（"距驱动沿"与"实际锁存"），让表的
  自洽性可以一眼核；并断言 `T_B = T_A + 8`（相位对称）。
- `rv32_pdm_clkgen.v` 头部与 P-04 的散文按新口径改写。
- 定下来的取点：`HOLD_TICK = 5`、`CONSUME_TICK = 13`（各距自己的驱动沿 150 ns，
  setup +41 ns / hold +60 ns；扫描出来的平衡点在 5.3）。

> ⚠ **更新（2026-10-10，同一天）**：取点随后按用户要求改回 **`4 / 12`**（采点 125 ns），
> 代价是 setup +41 → **+16 ns**。本文的根因（锁存时刻 = `(TICK+1)×25`）与指纹不变，
> 变的只是最后取哪一拍 —— 取舍与失效条件见 [093](093-sample-tick-moved-to-125ns.md)，
> 别按本文那句"定下来的取点"去找 5/13。

**复现指纹** 任何「第 N 拍做某事」的时序参数，先问一句：**是在第 N 拍的开始还是
结束生效？** 组合出来的 enable + 时钟沿消费的寄存器，答案一律是 N+1。
余量本来就只有一两拍的量级时，这一拍必须写进注释里。
