# 053 FFT 的 bank 没被推断成 RAM ⇒ 一个模块占掉 210% 的器件

**症状** 换 7020、卸掉杀软之后第一次跑通全流程（`synth_ok` → 实现），
`place_design` 直接失败：

```
ERROR: [DRC UTLZ-1] Resource utilization: LUT as Logic over-utilized
       This design requires 148380 of such cell types but only 53200
       compatible sites are available in the target device.
ERROR: [Vivado_Tcl 4-23] Error(s) found during DRC. Placer not run.
```

**148,380 / 53,200 = 279%。**

**误判** 第一反应必然是「设计太大了，得换更大的器件」。这个结论**不算错**
（确实装不下），但它会让你去讨论 7030/7045/7100 ——
而真正的问题是**一个模块本来不该占这么多**。

差一点就走了这条路：`149,009` 这个数字在综合阶段就报出来了，
和 `opt_design` 之后的 `148,380` **只差 0.4%** —— 看起来就是"设计确实这么大"。

**根因** 分层资源报告（`report_utilization -hierarchical`）一句话说清楚：

```
ps_pl_u_rv32_ps_0                149,009 LUT   ← 整个 PL
  u_soc                          147,302
    u_core                       139,822       ← 占 94%
      u_fft_bfly                 111,603  ← **占整个设计 75%，单它就 210% 器件**
      u_acoustic_ext              21,573
      u_vec_unit                   1,797
      （其余核内小块合计 ~4,800）
    其余全部（PDM 3,884 + ANC 2,943 + audio 1,111 + axi 856 + regs 626）
    ↑ 2026-10-03 当时的构成；ANC / audio 两块已于 2026-10-06 移除
                                  9,187
```

**`rv32_fft_bfly` 一个模块 = 111,603 LUT。拿掉它，剩 37,406 = 器件的 70%，装得下。**

再往下：`rtl/acoustic/rv32_fft_bfly.v` 第 58 行写着

```verilog
(* ram_style = "distributed" *) reg [31:0] bnk [0:NB-1][0:BW-1];
```

**8 bank × 64 字 × 32 位 = 16,384 位**，本该是 16 片 RAM32M 的活。
但报告里 **`LUTRAMs = 0`** —— **一片都没推断出来。**

原因就在同一段注释里，作者自己写了：

> ⚠ 这份 RTL 是**行为级**的：bank 用异步读（LUTRAM 风格），
>   **两个写口直接写在同一个数组上**。综合时每 bank 要落成两片 RAM32M
>   （2R1W × 2）才拿得到 2R2W

「**综合时每 bank 要落成两片 RAM32M**」是**人**才知道该怎么接的电路，
而代码里写的是「两个写口写同一个数组」。**RAM32M 是 2R1W**，
两个写口要变成 2R2W 必须**人工复制** —— 综合器的自动推断不做这件事。
推断失败之后它就退回最朴素的做法：**16,384 个触发器 + 全套读写多路选择**，
于是 111,603 个 LUT。

**这一条藏了十天，因为综合一直是坏的。** `docs/issues/039` 让这台机器
连 4 行 blink 都综合不了，`README` 里那句「资源与时序数字量不了」就是说它。
**代码里所有"综合时会怎样"的断言，在这十天里一条都没有被验证过。**

**实测：换 `ram_style` 属性一点用都没有（三种写法数字完全相同）**

单独综合 `rv32_fft_bfly`（`build/probe_fft_storage.tcl`），只改存储属性：

```
A 原样（ram_style = "distributed"）: LUT 121835
B 改成  (ram_style = "block")      : LUT 121835   ← 一个 LUT 都没省
C 属性整个删掉（让工具自己挑）      : LUT 121835   ← 还是同一个数
```

**三种写法给出逐位相同的 121,835。** 这坐实了根因是**代码结构**而不是配置：
`ram_style` 只是"你希望它落成什么"的**提示**，而综合器**做不到** ——
同一数组两个写口 + 组合读，没有任何原语能表达，于是提示被无视。

> ⚠ 探针里 FF / LUTRAM / BRAM / DSP 四列的过滤器**写错了**，三组都读 0
> （`PRIMITIVE_GROUP` 那类属性名没对上），**只有 LUT 那一列可信**。
> `LUTRAMs = 0` 这个结论取自**真设计**的 `report_utilization -hierarchical`，
> 那份是权威的，不依赖这个探针。
> 记在这里是因为"三列都读 0"本来就是个信号 —— 我扫了一眼才发现是自己过滤器的问题。

**推论**：修法一定是**结构性**的（改存储的读写结构，或显式例化原语），
不是"加个属性/加个 directive"能解决的。凡是看到"改了综合属性但资源数
一个都不动"，就是这一类 —— 参数扫不动是信号。

## 修复（2026-10-02）：关键是一条实测 —— **一个 RAM 只给一个写口**

一度按「换 BRAM」动手，改完 TB 逐位过了（513/513）但**综合出来 `RAMB=0`、
FF=16,945** —— 数组还是触发器。于是先停下来做模板对照
（`build/probe_tdp.tcl`，Vivado 2020.2，64 字 × 32 位，与每 bank 同尺寸）：

| 模板 | 结果 |
|---|---|
| 两个写口 + 两个读口，**同一个 always** | 工具明说 `RAM has multiple writes via different ports in same process`，**dissolved into registers** |
| 两个写口各占一个 always | `ERROR [Synth 8-2914] Unsupported RAM template` |
| 写口一个进程、读口另一个进程 | 同第一条（两个写口仍在同一进程） |
| **1 写 + 1 读**（`ram_style="block"`） | **`RAMB=1`** ✓ |
| **1 写 + 2 异步读**（`distributed`） | **`RAM=112`，LUT=0、FF=0** ✓ 工具自动复制副本 |

**结论：真双口（两个写口）推不出来，必须实例化原语；「1 写 + N 异步读」能推。**
⇒ 真正的修法不是换 BRAM，是**把每个 bank 的写口降到 1 个**。

⚠ 顺带修正本档上面那条建议：**BRAM 虽然能推（1 写 1 读），但它读有 1 拍延迟**，
会把每个发生器周期都撑成「读相 / 写相」两拍，拍数要再翻一倍。
而分布式 RAM **可以异步读**，读没有延迟 —— 这条差别决定了拍数差一倍。

### 改法

**地址有一条硬性质：窗口基址恒 8 对齐** ⇒ 一个发生器周期里所有 bank 的
字号都相同（`wa[8:3]`），bank 号就等于窗口内偏移。于是每个 bank 每拍要几条写，
是可以数出来的：

| 级 | a' 与 b' 落在哪 | 每 bank 每拍写口数 | 拍数 |
|---|---|---|---|
| mode4（stage 0..2） | **不同 bank**（a 槽的 half 位恒 0，`own[g]`/`own[g^half]` 恰一个为真） | **1** | 一拍一组（不变） |
| mode8（stage 3..8） | 同一个 bank、**不同字**（A 窗 / B 窗） | **2** | 拆成两拍 |

拆分的两条写（`X[k]` 与 `X[512−k]`）落在**不同 bank** 时同拍写；只有
`kk[2:0]==mm[2:0]`（257 次里的 65 次）才多花一拍。

⚠ **两个坑，都是"换存储"才会冒出来的**：
1. mode8 第 0 拍写完 a' 之后，**A 窗的异步读就变成 a' 了**（B 窗没动）。
   第 1 拍要用的 b' 必须**在第 0 拍就寄存**（`b2r_q/b2i_q`），
   否则 `ar` 被自己的写回污染。拆分撞 bank 时同理（`xi2_q/xr2_q`）。
2. 上面那个寄存**不能无脑套用到两条路**：`X[m]` 在**不撞 bank** 时与 `X[k]`
   同拍写，那一拍两窗都还没脏 ⇒ 必须用**组合值**。两条路都取寄存值时
   会写出上一个 k 的陈旧结果，指纹是 **bin 0..256 全对、257 以后全错**
   （和本档 §6 记的那个"原地覆盖"指纹一模一样，但**根因完全不同**）。

### 实测结果

| | LUT | FF | LUTRAM 原语 | 9 级+拆分拍数 |
|---|---:|---:|---:|---:|
| 修复前 | **121,835** | 16,945 | 0 | 645 |
| 修复后 | **5,268** | 337 | 896 | **900** |

**LUT 降 23 倍，拍数只涨 1.40 倍。** 单元级 2695 → **2950** 拍，
端到端（含核侧 `lw`/`sw`）7342 → **7597** 拍（**26.18×**，原 27.09×）。

TB 仍然 **513/513 逐位一致**（对同一份 `build/fw_fft_ref.hex`）。

### ⚠ 先纠正一个我自己差点推荐错的方向：RAM32M 不是 2R2W

一度打算推荐「显式例化 RAM32M」—— 理由看着很顺：它体积小、异步读、
**拍数 288 一拍不用改**。而且 Vivado 自带它的仿真源码
（`$VIVADO/data/verilog/src/unisims/RAM32M.v`，iverilog 能直接编），
所以"原语没法仿真"这个顾虑也不成立。

**读了那个模型之后发现前提是错的：**

```verilog
always @(posedge WCLK_in) if (WE_in) begin   // ← **只有一个写口**（ADDRD）
    mem_a[..] <= DIA_in;  mem_b[..] <= DIB_in;
    mem_c[..] <= DIC_in;  mem_d[..] <= DID_in;  //   四个数据面在**同一地址**一起写
end
assign DOA[..] = mem_a[2*ADDRA];             // ← 四个**独立异步读口**
assign DOB[..] = mem_b[2*ADDRB];
```

**RAM32M 是 4R1W，不是 2R2W。**

顺带说明 `rv32_fft_bfly` 头注释里那句
「每 bank 要落成**两片 RAM32M（2R1W × 2）**才拿得到 2R2W」**有两处不对**：
RAM32M 不是 2R1W；而且两片 RAM32M 各有各的写口，
各写各的会让两份副本**不一致**，读的时候无从判断该信哪一份 ——
**2 个独立写口 + 2 个独立读口，用 RAM32M 拼不出来。**

（这个错差点写进推荐里。**"先读原语的行为模型再推荐它"** 这一步救回来了。）

### 四条路（修正后）

| 方案 | 代价 | 风险 |
|---|---|---|
| ~~显式例化 RAM32M~~ | ~~288 拍不变~~ | **不通**：RAM32M 是 4R1W，拼不出 2 个独立写口 |
| **换成 BRAM（RAMB36 真双口 = 真 2R2W）** | 8 片 BRAM36（每片只用 2Kb / 36Kb），LUT 几乎清零 | **读延迟从组合变 1 拍** ⇒ 288 → 576 拍，golden 与拍数基线要重验 |
| **降到 1R1W + 2 拍/级** | 结构最简单，推断最容易成 | 同样 576 拍 |
| **换更大的器件** | 不用改 RTL | 7030（106K LUT）才刚好，7100 才宽裕；**问题没解决只是被掩盖** |

**修正后的建议：换 BRAM。** 它是唯一能给**真 2R2W**（RAMB36 的 TDP 模式）
且**保持可验证**（纯行为级描述，iverilog 与 Vivado 语义一致）的路。
代价是拍数翻倍、README §0.8 的 27.09× 要重测 —— 但那个数字**本来就没在真器件上量过**。

`vfft_design.md` 与 `fw_fft` 的拍数基线都会跟着变，所以这不是我能替用户定的。

**复现指纹** **报告里 `LUTRAMs = 0`，而代码里明明写了 `ram_style="distributed"`**
⇒ 推断失败了，不是"这个模块本来就这么大"。凡是"某个模块大得不成比例"，
先去看它的存储是不是落成了触发器 + 多路选择，而不是先怪设计。
