# 060 `rv32_acoustic_ext` 三个数组也没进 RAM ⇒ 它一个模块占全 PL 的 54%

**状态**：**已修**

**症状** 修完 [053](053-fft-storage-not-inferred.md)（FFT 的 bank 换存储）之后，设计
装得下了（LUT 39,815 / 53,200 = 74.8%），但**时序差 0.604 ns 收不了**，而且
关键路径的形状很特别：

```
Data Path Delay: 25.364ns  (logic 10.994 (43.3%) + **route 14.370 (56.7%)**)
```

**56% 是布线**，每根网 0.48 ns。对比 09-20 的记录：同一条路径、**同样的逻辑深度**
（10.6 ns / 28 级），布线只有 11.8 ns —— **两周里涨的 2.6 ns 全是布线**。
那条路径本身（核的 EX/MEM payload 组合闭环）没变，**是它周围变挤了**。

**误判** 先按 [025](025-routing-dominated-critical-path.md) 的配方试"布线后补 phys_opt"：
在 −1.5 ns 时有效（挪到 −0.616），**再迭代两遍就收敛不动了**（−0.616 / −0.604）。
又试了 `Performance_RefinePlacement` —— **−2.822，更差**。
两条路都堵死，说明问题不在摆位算法，在**布局里塞了不该塞的东西**。

**根因** 分层资源报告里那一列：

```
u_acoustic_ext   21417 LUT | LUT as Logic 21417 | **LUT as Memory 0** | FF 7007 | DSP 56
u_fft_bfly        5569 LUT | LUT as Logic  4865 |     LUT as Memory 704 | FF  337
```

`u_fft_bfly` 有 704 个 LUTRAM（053 修好的），而 **`u_acoustic_ext` 是 0** ——
它的三个数组 `mx`/`my`/`mz`（各 208×32）**一片 RAM 都没进去**，
而它是**全设计最大的单块：21,417 LUT = 全 PL 的 54%**。它就是"挤"的来源。

**三个独立的原因，一个一个量出来的**（`build/probe_*` 全是同尺寸对照）：

| # | 原因 | 证据 | 修法 |
|---|---|---|---|
| ① | **端口数超限**：`mx` 被读了两遍（复数乘 8 个 lane + VRED2 归约 8 个 lane）= **1 写 + 16 读 = 17 个口**，而分布式 RAM 上限是 **16** | `1写+8读 → LUTRAM=1792 ✓`；`1写+16读 → dissolved ✗` | 两组读地址**完全相同**（都是 `base+k`）⇒ 共用一根读数据线 |
| ② | **写落在带异步复位的 always 里**：分布式 RAM **没有复位端**，工具看到 `negedge rst_n_i` 就要求数组也能复位 | `裸 if(we)、无复位 → LUTRAM=1792 ✓`；`写嵌在带异步复位的 FSM 里 → LUTRAM=0 ✗`。另两个对照排除了"深度 208 不是 2 的幂"和"深度用 localparam 表达式" | 把 PUSH 的落盘拆到**单独一个不带复位的 always** |
| ③ | **`mz` 每拍写 8 个不同的字**（`for k: mz[base+k] <= ...`，每 lane 一个）= 8 个写口 | `1写+8读 ✓` vs `8写+1读 → dissolved ✗` | 按 lane 分 8 个 bank（见下） |

**`mz` 能按 lane 分 bank，是因为 `base = pass×8` 恒是 8 的倍数**：

```
全局下标 i  →  bank = i & 7，字 = i >> 3
写：lane k 写下标 base+k  ⇒  bank = k、字 = pass   ← 地址是**静态的**，不用译码
读：lane k 读下标 base+k  ⇒ 同一地址
POP：读 mzb[ptr[2:0]][ptr[7:3]] —— 8 个 bank 同字读出，再按 ptr[2:0] 选
```

**这与 053 修 FFT bank 是同一手法**：把写口降到每 bank 一个。

**实测（模块级，out-of-context 综合）**

| | 起始 | 修后 | |
|---|---:|---:|---|
| **LUT** | 26,455 | **4,290** | ↓6.2× |
| **FF** | 20,269 | **275** | ↓74× |
| LUTRAM | 0 | **3,971** | ✓ |
| DSP | 56 | 56 | 不变 |

功能：`tb_acoustic_ext` **VCMUL/VSUB/VPHAT 各 0/208 条不符**，
`tb_fw_gcc` / `tb_fw_srp` 端到端逐位一致 —— **算术一个字没改，只动了存储的摆放**。

## ⚠ 反证：这一大块收益**没有**换来时序改善

**我当时的假设是**：全 PL 74.8% → 拥挤 → 关键路径 56% 是布线 → 压掉 54% 的 LUT
就能让布线变短 → 时序收口。

**实测把这个假设推翻了**（Zynq 全流程，40 MHz）：

| | 修 `u_acoustic_ext` 之前 | 之后 |
|---|---:|---:|
| **Slice LUTs** | 39,815（**74.8%**） | **24,040（45.2%）** ✓ |
| Slice Registers | 21,265 | 14,508 |
| **WNS** | −0.604 | **−0.777** ✗ |
| **失效端点** | 163 | **189** ✗ |
| TNS | −34.57 | −53.43 ✗ |

**LUT 少了 15,775 个（占器件的 29.6%），WNS 反而差 0.17 ns。**

⇒ **"全局拥挤撑长了关键路径的布线"这个因果是错的。**
那条路径（`u_ex_mem_reg/u_payload_dff` → SoC 译码 → 回来）的布线长短，
取决于**源与目的在物理上离得远**，与全设计占用多少无关 ——
这正是 [025](025-routing-dominated-critical-path.md) 当初的结论，我绕了一圈又回到它。

**教训（比收益本身更值钱）**：
1. **"省了资源"和"修好时序"是两件事，没有因果关系。**
   改之前我该先问一句：如果这不是拥挤造成的，那 `LUT 74.8% → 45.2%` 能改变什么？
   ——答案是**什么都不改变**，因为路径长度由两端位置决定。
2. **布局后 WNS 是个便宜的判据**：那次 `Post Placement WNS −1.473 vs 上一轮 −1.373`
   （几乎没动）**在布线之前就已经预告了这个结果**。当时我看到了，但选择"等最终数字"，
   白跑了一轮 40 分钟的流程。**下次看到布局后没动，就该停下来重新想，而不是等布线。**

**所以这一条的适用边界**：它是**资源与可布线性**的修复（设计从 74.8% 降到 45.2%，
F7/F8 mux 降到 1/5，为后面加东西腾出了空间），**不是时序修复**。
时序那条线仍欠着，见 [057](057-first-real-timing-measurement.md) 的"还欠的"。

---

**指纹（这次最值钱的三条）**
1. **`LUT as Memory = 0` 而代码里明明写了 `ram_style="distributed"`** ⇒ 推断失败了，
   不是"这个模块本来就该这么大"（和 053 同一条）。
2. **`FF` 的数量约等于数组的总位数**（20,269 ≈ 3×208×32 = 19,968）⇒ **铁证**：
   数组整个落成了触发器。看到这个数就不用再猜了。
3. **端口数超限的报错只说"reason is one or more of the following"**，不告诉你哪一条；
   要靠**同尺寸的最小对照**逐个排除。053 也是这么找到 2 写口的。
4. ⚠ **"写口减到 1 个"还不够** —— 那个写所在的 always **不能带异步复位**。
   053 只讲了前半句，这一条是它的另一半，两条合起来才完整。
