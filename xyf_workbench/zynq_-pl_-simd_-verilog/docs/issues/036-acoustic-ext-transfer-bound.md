# 036 声学扩展指令：算得飞快，但被搬运吃光（附带四个 RTL 坑）

**状态**：已修 / **设计待改进**（搬运路径）
**日期**：2026-09-22
**阶段**：Stage 1（声学 DSP 扩展指令落地）
**复现**：`tb/tb_acoustic_ext.v`

---

## 结果先说：四条指令都对，但**几乎白干**

`rv32_defines.vh` 里声明了很久、一直只有编码没有单元的 VCMUL / VPHAT /
VSUB / VRED2，这一轮补上了 `rtl/acoustic/rv32_acoustic_ext.v`，
四条都通过了与定点模型的**逐位比对**（`scripts/golden/fw_acou_model.py`）。

然后量拍数（512 条复数）：

| 阶段 | 单元级 TB 实测 | **真实固件（含 lw/sw）** |
|---|---:|---:|
| 装载 X + Y（1024 次 PUSH） | 3072 | **5120** |
| VCMUL（64 趟 × 8 lane） | **68** | **68** |
| 取回 Z（512 次 POP） | 1536 | **2560** |
| **合计** | 4676 | **≈ 7748** |
| 标量对照（512 条复数乘） | ~7680 | ~7680 |

> ⚠ **订正（同日）**：本档案最初只写了 TB 那列，结论是「搬运占 98.5%」。
> 那个数**偏乐观** —— TB 把 `scalar` 直接喂给单元，**没有 `lw`**。
> 真实固件里每条 PUSH 前面都得先 `lw` 一次（DTCM 隔拍应答，2 拍），
> 取回也要 `sw`。按真实口径，总拍数 **≈7748，与标量 7680 基本持平**。
> 所以正确的结论不是「快 1.64 倍」，而是**「不改搬运路径的话，这条指令基本是白干」**。

**运算部分快了 113 倍（68 vs 7680），整条却是 1.0 倍。**
快的那部分只占 0.9%，剩下的全是搬进搬出。

## 根因

操作数靠核一条 `PUSH` 灌一条复数（32 位 = 一条复数），一次 3 拍
（start / done / commit 握手）。真实固件每条还要加一次 `lw`。

**这不是实现没写好，是接口选错了**：频谱本来就在 DTCM 里（FFT 的输出），
把它搬进单元、算完再搬回去，等于为了用一条指令付两遍搬运。

## ①② 已做（同日）—— 搬运少 3.66×，但**端到端只快 4.4%**

**做法**（`rtl/acoustic/rv32_acoustic_ext.v`）：

- **只搬带内**：存储只放 bin 6…209（208 条，补到 8 的整数倍）。带外注定要清 0
  （README §0.3.4 第 1 条），**搬它没有意义**。存储也从 512 条缩到 208 条
  （LUTRAM 6 KB → 2.4 KB）。
- **单拍 PUSH/POP**：不再走多拍单元的 start/done/commit（3 拍），改成
  **一条 1 拍**。判据用 `commit_i`（"这条指令正被 EX/MEM 收下"）而不是 start 的
  上升沿 —— 用沿检测的话，**背靠背连续 PUSH 会被吃掉**（start 一直为高时没有"沿"）。

**实测（单元级）**：

| | 旧（512 条整段 + 3 拍握手） | **新（208 条带内 + 1 拍）** |
|---|---:|---:|
| 装载 X+Y | 3072 | **832** |
| VCMUL（26 趟） | 68 | **30** |
| 取回 Z | 1536 | **416** |
| **合计** | **4676** | **1278** |

**3.66×** —— 四条指令仍然逐位正确。

### ⚠ 但端到端只有 4.4%，因为我加速错了那一段

> ⚠ **2026-10-04 记**：下表是**当时那一版固件**的实测。固件后来又改过，现在
> `tb_fw_fft` / `tb_fw_gcc` 报的是标量 FFT **198905** 拍、GCC-PHAT 一对 **673534** 拍
> （本表写的是 199056 / 673511）。差 ~150 拍摊到 76343 拍的互谱循环上可忽略，
> **下面的结论（1.044×）不受影响**。留在这里不改成新数，是因为它是那次测量的
> 原始记录；**要引用请用 TB 当场报的数**。

把已实测的几个数摆在一起（**全是实测**，只有带内折算与 `lw/sw` 是推的）：

```
GCC-PHAT 总           673511 拍   ← 实测
  其中 2×FFT          398112      ← 实测（2 × 199056）
  其中 IFFT           199056      ← 实测
  其中 互谱+白化循环    76343      ← 相减得出，513 条 ⇒ 148.8 拍/bin
      带内 204 条 ⇒   30359 拍    ← 推的（按条数折算）

声学路径（含核侧 lw/sw 估算）≈ 1932 拍  ← 单元级 1278 实测 + 60% 估计
  ⇒ 这一级加速 15.7×
  ⇒ 端到端 673511 → 645084，**仅 1.044×**
```

**根因：FFT + IFFT 占 GCC-PHAT 的 88.7%，互谱/白化只占 11.3%。**
声学扩展的四条指令（复数乘、白化、共轭乘、对偶归约）**全部落在那 11.3% 上**，
一条都不碰 FFT 蝶形。把 11% 加速 15.7 倍，整条最多快 4%。

**这是这一轮最值钱的一条结论**：不是搬运没优化好，是**优化的目标选错了**。

### 所以下一步不是继续修搬运

| 选项 | 预期 | 该不该做 |
|---|---|---|
| 继续压搬运（借 DTCM A 口等） | 端到端再快不到 2% | **不值得** |
| **把加速指向 FFT 蝶形**（占 88.7%） | 才是真旋钮 | **应该做** |
| 固定功能流水（`rv32_xspec_phat.v` 那条路） | 数据不经过核，搬运归零 | 退路，会削弱"自研核"的叙事 |

**FFT 蝶形怎么加速**（下一步的设计方向，还没做）：
蝶形是 `a±w·b` 的形状，8 lane 一次做 8 个蝶形，因子按 lane 广播。
难点在**数据布局**：蝶形要在数组上做跨步访问，而现有阵列的延迟线是按
样本下标分 bank 的。**先把「每个蝶形的访存模式」量清楚，再决定 bank 怎么划** ——
不要先改 RTL。

## 这一轮踩的四个 RTL 坑（都是"不报错、只算错"）

1. **指针每次 commit 都清零** → 512 次 PUSH 全落在同一个地址，只有 `mx[0]`
   有值、其余是 X。PUSH 一个个"成功"返回，看起来完全正常。
   第一次改成「POP 之后清零」，又变成 **POP 每次读完就回到 0**，整条序列错位
   一格：**第一个值对、后面全差一个**。正确做法是**只在计算类指令收尾时清零**，
   PUSH/POP 各自扫满 512 次自然回绕。
2. **POP 的自增发生在读之前**。`result_o` 是组合的，而 `done` 比 `start` 晚一拍，
   那一拍指针已经加过了。修法：start 当拍把 `mz[ptr]` 寄存进 `rd_q`，`done`
   那拍输出 `rd_q`。**错一格的相关序列看着仍然"像相关的样子"**，最难发现。
3. **`for` 循环里对同一寄存器多次非阻塞赋值**：`for (k) acc <= acc + mx[base+k];`
   只有最后一次生效 —— 每拍只加了 8 条里的最后一条，归约值偏小 8 倍。
   修法：先组合求和，再一次性累加。
4. **VPHAT 每拍只处理了一条复数**（其余 ops 都是 LANES 条）。512 条里只有 64 条
   被白化，其余保留互谱原值 —— 带内确实变平坦了，**看起来像白化成功**。

四个的共同点：**结果都是"合理的数字"**。这就是为什么这一轮每个都靠
「与定点模型逐位比」才抓出来 —— 目测波形、看频谱、看量级，一个都发现不了。

## 留下的教训

- **新单元一定要先做"逐位对照"的单元级 TB，不要直接塞进核里联调。**
  这一轮的四个坑里，有三个在单元级就暴露了；塞进核里之后，同样的错会表现为
  「固件的互谱结果不对」，而那要跑 270 万拍才能看出来。
- **先量搬运，再优化运算。** 运算快了 113 倍这个数字很漂亮，但整条是 1.0 倍。
  只报前者的后果，看这份档案的两版结论就知道了 —— **第一版写的是「1.64 倍」，
  那也是错的**，因为单元级 TB 没有 `lw`。
  **判据要按"最终形态"去设**：验单元时顺手把 `lw/sw` 算进去，就不会有这一版订正。
- **"单元级 TB 通过"不等于"用起来有收益"。** 它只证明**算得对**。
  收益要在真实调用路径上量 —— 这一轮的量法是把 TB 的拍数账分成
  「装载 / 运算 / 取回」三段，一眼就看出哪一段是大头。
  `tb_acoustic_ext.v` 里那几行拍数账是这一轮最值钱的产物。
