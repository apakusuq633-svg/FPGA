# 048 `check` 任务的中文消息被打散成乱码方块 ⇒ FAIL 了却读不出是哪一条

**症状** `tb_pdm_capture` 报 8 项失败，但每一条都长这样：

```
FAIL: ����������������� SE�������� = 1  (t=3913000)
FAIL: ACK������������� RELEAS����������� bank��������������������  (t=16913000)
```

只有 ASCII 片段（`SE`、`= 1`、`ACK`、`RELEAS`、`bank`）能认出来，
中文全成了 `�`。**FAIL 了却不知道是哪一条** —— 比没有 FAIL 更费时间，
因为还得靠"第几段第几个"去反推。

**误判** 先以为是终端编码问题（Windows 控制台 GBK），于是把输出重定向到文件再读。
文件里**同样是乱码** ⇒ 不是终端，是字符串本身在 TB 里就已经坏了。

**根因** 消息是通过 `input [8*160-1:0] msg` 传进 task 的。中文串是 UTF-8 多字节，
赋给这个打包向量时被按字节摆位，`%0s` 打出来就散了。
**同一个仓库的 `tb_pdm_array_rx` 也有这个问题**，只是当时那几条恰好没触发
（或者触发了我没注意 —— 回头看它那次 FAIL 输出，确实是同样的乱码）。

直接 `$display("...中文...")` 用字面量是**没问题**的（测试里那些 ✓ 行都是中文，
打印正常）。坏的只有「中文串 → 打包向量 → `%0s`」这条路径。

**修法** `check` 的消息串一律改成 ASCII 短标签（`"bank0 must be ready after CAP frames"`）。
注释仍然是中文 —— 注释不经过这条路径，不受影响。

**复现指纹** `$display` 的中文字面量正常、但经 task 传进来的中文是方块
⇒ 不要再查终端和重定向，直接改成 ASCII。
