# 034 头文件里的 `static const` 数组被每个 .c 各存一份

**状态**：已修
**日期**：2026-09-22
**阶段**：Stage 1（GCC-PHAT 固件内核，DTCM 预算）
**复现**：`bash scripts/build_fw.sh`（看 `.data` 段大小）

---

## 症状

旋转因子表（513 条复数、Q14 int16）由 `scripts/golden/fw_fft_model.py` 生成
成 `sw/fw/fw_tables.h`，里面是：

```c
static const int16_t g_tw_re[FW_TW_N] = { ... };   /* 1026 B */
static const int16_t g_tw_im[FW_TW_N] = { ... };   /* 1026 B */
```

三个 .c 包含它（`fw_fft.c` / `fw_gcc.c` / 间接经 `fw_fft.h`）。构建输出：

```
   .data 0x00000000 + 0x00000c0c -> 结束于 0xc0c      ← 3084 B
```

表本体只有 **2052 B**，却占了 3084 B —— 多出来的 1032 B 是**第二份副本**。
（`.data` 里还有别的小东西，所以不是整数倍。）

**不报任何错**，只是 `.data` 悄悄变大，把 `.bss` 挤到 `0x2400` 的边界外面：

```
!! .bss 撞上批量输出区 0x2400。缩缓冲区，或挪 .fwout。
```

## 误判

第一反应是**缓冲区开多了**，于是去算 GCC-PHAT 到底要几块内存。
算了半天发现每块都"确实需要"，怎么都省不出 1.3 KB。

**问题不在缓冲区，在常量表。** 是 `.data` 先悄悄多吃了一份，`.bss` 才不够的。
（`build_fw.sh` 的守卫报的是 `.bss`，指向的是症状不是原因。）

## 根因

**`static` 在头文件里的语义是「每个翻译单元一份」。**

```c
/* fw_tables.h */
static const int16_t g_tw_re[1026] = { ... };
```

这段被 3 个 .c 包含 ⇒ 链接后 `.data` 里**有 3 份**（链接器不会合并
`static` 对象，因为它们内部链接、按定义就是各自独立的）。

2052 × 3 ≈ 6 KB —— 在 DTCM 只有 16 KB 的机器上，这是要命的量级。
（实测只看到 2 份的效果，是因为其中一份被 GCC 内联/优化掉了一部分。）

## 修法

生成器改成**吐两个文件**：

| 文件 | 内容 |
|---|---|
| `sw/fw/fw_tables.h` | 只有 `extern` 声明 + `#define` |
| `sw/fw/fw_tables.c` | 唯一的定义 |

`build_fw.sh` 把 `fw_tables.c` 加进编译和链接。

修完：`.data` 回到 **2056 B**，`.bss` 结束于 0x2110，都在界内。

## 复现指纹

- **`.data` 比常量表本体大**（尤其"大出来的量 ≈ 表大小 × 包含它的 .c 个数"）
  ⇒ 十有八九是头文件里的 `static` 定义。
- 一条命令认出来：

  ```bash
  riscv64-unknown-elf-nm -S --size-sort sw/fw/fw.elf | grep -i tw
  ```
  同名符号出现多次 ⇒ 就是它。

## 留下的教训

- **头文件里不要放定义**，哪怕加了 `static`。"static 只在本文件可见"是对的，
  但"本文件"有 3 个的时候，就是 3 份。
- **生成代码尤其危险**：手写的表通常只有一处引用，而生成的表往往被多个模块
  共用（FFT 要用、Hann 窗要用、逆变换要用）—— 正好是触发这个坑的形状。
- 这个坑和 `docs/issues/019`（Verilog/C 常量漂移）是**同一类**：
  同一份数据在两处各存一份，谁都不报错。019 的做法是让生成器同时吐 `.h`；
  这一次是让生成器**多吐一个 `.c`** —— 生成器本身就是那道防线。
