# 032 输出区地址口径漂移：固件写在 0x2000，TB 读 0x2400

**状态**：已修
**日期**：2026-09-22
**阶段**：Stage 1（FFT 内核联调）
**复现**：`tb/tb_fw_fft.v`

---

## 症状

FFT 内核单独验过：同一份 `sw/fw/fw_fft.c` 编到 x86 上跑，
对着 Python 定点模型 **0/513 条不符**。搬到真核上跑仿真：

```
首个不符: bin 0  实测 re=-28 im=180  期望 re=-104 im=0
定点参照比对: 513/513 条不符
X[16] 幅度: 实测 192.1  独立复算 6523.0  相对差 97.06%
```

而**固件自己报的峰值 bin 是对的（16）** —— 这一条最迷惑人：
既然固件读回来的峰值都对，说明它算得没错，那"错"的到底是谁？

## 误判

顺着「固件算得对、TB 读得不对」往下想，怀疑过三条：

1. **`sh` / `lh` 的字节落点**。`rv32_soc.v` 里有一句「只支持整字 `sw`，
   `sb`/`sh` 会让字节落到 `dmem_wdata` 高位」—— 差点就去改 LSU。
   **但那是 MMIO 寄存器的限制**（它们直接用 `dmem_wdata`，不过字节使能）；
   DTCM 走的是 `wstrb`，`sh` 在 `0x2400`/`0x2402` 分别写低半/高半，
   完全正确。读了一遍 `rv32_lsu.v` 才排除。
2. **旋转因子表没装进去**。DTCM 里 dump 出来是 `40004000` / `ff9b0000`，
   与 `fw_tables.h` 一字不差，排除。
3. **输入帧没造出来**。dump DTCM `0x908`（`g_frame`），与 TB 自己按同一公式
   造的两两相等，排除。

排到最后只剩「写」和「读」不在同一块地方。

## 根因

**`fw_main.c` 里的 `FW_OUT_BASE` 还是 `0x2000`，而 `link.ld` 的 `.fwout`
已经挪到 `0x2400`。**

中间我为了给 `.bss` 腾地方，把固定输出区从 `0x2000` 挪到了 `0x2400`，
**只改了链接脚本**。固件那边是个 `#define`，不参与链接，改了链接脚本它
一声不响地继续往 `0x2000` 写。

`0x2000` 落在 `.bss` 末尾（`0x1d08`）和 `.fwout`（`0x2400`）之间 ——
**一块谁都不用的空地**。于是：

- 固件写 `0x2000`、读 `0x2000` → 自洽 → **峰值 bin 报得完全正确**
- TB 读 `0x2400` → 那里是 X/旧值 → 全是小数

「固件自洽但和外部观察者不一致」正是这类 bug 的指纹。

## 修法

`fw_main.c` 的 `FW_OUT_BASE` 改成 `0x2400`，并在定义处写明：

> ⚠ 这个地址必须与 link.ld 的 `.fwout` 一字不差。改了一处没改另一处的现象是
> 「FFT 输出全是小数」，看上去像算法错。

## 复现指纹

- **固件自己的指纹对、TB 的指纹不对** ⇒ 先怀疑两边读的不是同一块地址，
  不要去查算法。
- 最省事的判定：让 TB 把「固件写的那块」和「TB 读的那块」各 dump 几个字，
  并排打出来。本例一 dump 就看见 `g_frame` 和因子表都对，只有输出区不对。

## 连带修正（TB 自身两个坑，都是报错信息指错方向的那种）

1. **`tri` 是 Verilog 保留字**（三态线网）。写成 `integer ph, tri, noise;`
   报的是 `invalid module item`，看上去像声明语法错，其实是撞关键字。
   改名 `tri_v`。
2. **函数返回值不能直接位选**：`$signed(outw(k)[15:0])` 不是合法 Verilog。
   先落一个 `reg [31:0] wtmp;` 再选位。

## 复发（同日，TB 侧）

把 `.fwout` 从 `0x2400` 再挪到 `0x2800` 时，**`tb/tb_fw_fft.v` 的 `OUTW` 常量
没跟着改**（`32'h2400 >> 2`），于是它读的是空闲区 —— 报出来是
「FFT 输出与定点参照全不符」。

和第一次一模一样的形状：**同一个地址在三个地方各写一遍**
（`link.ld`、`fw_mem.h`、TB 的 `localparam`）。第一次漏了中间那个，
这次漏了 TB 那个。

**收敛做法**：`fw_mem.h` 里已经把三个区的地址集中了，TB 拿不到 C 宏，
所以只能靠「改地址时全仓 grep 一遍十六进制」这条纪律。
**下次再动这些地址，先 `grep -rn "0x2400\|0x2800\|0x3080" sw tb scripts`。**

## 留下的教训

- **同一件事在两个文件里各写一遍，就必须有一条机器检查把它们钉在一起。**
  这里 `0x2400` 在 `link.ld` 和 `fw_main.c` 各写了一次，谁都没错，合起来是错的。
  同类的还有 `docs/issues/019`（Verilog/C 常量漂移）——
  **那次的做法是让生成器同时吐 `.h`**，这次没有生成器，靠注释和这条档案。
- 更好的一层防线是**分层验证的顺序**：host 侧先过（秒级），再过仿真。
  本例里 host 侧 `0/513 条不符` 直接把「算法错」排除掉了，剩下的搜索空间
  小得多 —— 这个 `scripts/golden/fw_fft_host_check.sh` 就是为它建的。
