# 031 固件读不到任何常量表（`.rodata` / `.data` 初值全是 X）

**状态**：已修
**日期**：2026-09-22
**阶段**：Stage 1（RV32 固件构建流 → 第一个真内核 FFT）
**复现**：`tb/tb_fw_smoke.v`（探针段）、`tb/tb_fw_fft.v`

---

## 症状

写 FFT 需要一张旋转因子表，于是加了一段探针：

```c
static const int16_t g_tab_ro[8] = { 10, 20, 30, ... };   /* 期望和 360  */
static int16_t       g_tab_data[4] = { 555, 666, ... };   /* 期望和 2886 */
```

结果**两个都是 `x`**：

```
RES(6)  = xxxxxxxx      ← 常量表
RES(14) = xxxxxxxx      ← 有初值的全局变量
```

而同一份固件里，运行期算出来的点积 / FIR / 能量**三个数全对**。
所以不是核坏了、不是存储坏了 —— 是**只有「从内存里读常量」这一条路**断了。

## 误判

第一反应：核的访存端口按地址译码，`0x0000–0x1FFF` 落到 DTCM 而 `.rodata`
在 ITCM 地址段，所以 `lw` 读到的是 DTCM 同地址的内容。

**这个判断是对的，但不是这次的主因** —— 我按这个思路改了 `rv32_itcm`
（加了一路核侧数据只读口）和 `rv32_soc`（低 8 KB 改走 ITCM），结果：

1. 探针**还是 x**；
2. 顺手打断了 5 个老 TB（`tb_rv32_soc` / `tb_rv32_ps` / `tb_vec_core` /
   `tb_anc_hybrid` / `tb_audio_loop`）—— 它们**故意**把数据放在 DTCM
   `0x0000` 起（`tb_vec_core` 的注释就写着「DTCM 字基址」）。

**先量再改**这条又栽了一次：改之前没有先看一眼符号地址。

## 根因（两个，叠在一起）

### 1. 链接脚本漏了小数据段 —— 主因

`nm` 一跑就清楚了：

```
00002008 d g_tab_const      ← 常量在 0x2008，DTCM 里，根本不在代码段！
00002000 d g_tab_data
```

`link.ld` 里写的是：

```
.text { *(.text*) *(.rodata*) }
.data { *(.data*) }
```

**`*(.rodata*)` 匹配不到 `.srodata`，`*(.data*)` 匹配不到 `.sdata`。**
GCC 把小的常量/变量放进 `.srodata` / `.sdata`（小数据段优化），这两个段
**没有任何输出段接住**，成了**孤儿段**：ld 把它们丢到默认位置（实测正好落在
DTCM 0x2000 起，和 `.data` 挨着），**初值也一并丢掉**。

于是：
- `.srodata` 里的常量：地址在 DTCM，而镜像根本没往那儿写过 → 读出来是 X
- `.sdata` 里的变量：镜像里有初值，但**启动拷贝循环只覆盖 `.data` 的
  `_data_start.._data_end`**，`.sdata` 不在区间里 → 从来没被拷过 → 也是 X

### 2. 核的数据端口到不了 ITCM —— 潜伏的第二个

即使把 `.srodata` 归进 `.text`（地址 < 0x2000），`lw` 也读不到：
`rv32_soc` 里 `dtcm_req = dmem_req & ~dmem_mmio` —— **所有**数据访问都打到
DTCM，ITCM 只有取指口和 PS 口。放在 `0x0000–0x1FFF` 的常量，用 `lw` 读到的
是 DTCM 同地址的内容。

同理，旧版 `start.S` 那句「从 ITCM 的 LMA 拷 .data」：

```asm
la  t0, _data_lma      /* LMA 在 ITCM 地址段 */
lw  t3, 0(t0)          /* 但这是数据访问 → 打到 DTCM → 读到垃圾 */
sw  t3, 0(t1)
```

**这个循环从来没真正工作过**，只是从前固件里没有带初值的数据，没人发现。
`link.ld` 头部那句「走启动拷贝这条路对上板同样成立」是**基于一个错误的假设**。

## 修法

**不碰 RTL**，把常量与初值改成随 **DTCM 镜像**预装。理由：

- 核数据口到不了 ITCM 是**设计选择**（两块存储器地址重叠、由端口区分），
  不是 bug；改它要动译码，还会打断老 TB 的既有用法（实测过，见「误判」）。
- 上板时 PS 本来就有写 DTCM 的通路（`rv32_ps_memif` 的 `MEM_SEL_DTCM`），
  预装 DTCM 不是仿真专有机制。

具体：

| 文件 | 改动 |
|---|---|
| `sw/fw/link.ld` | `.rodata`/`.srodata` 并进 `.data`；`.data` 的 **VMA = LMA = DTCM 0x0000**（由加载方预装）；`.sdata` 显式写出；ITCM/DTCM 声明成两个 MEMORY region（否则 ld 按地址判 LMA 重叠直接报错） |
| `sw/fw/start.S` | **删掉** `.data` 搬运循环（搬不了，见根因 2），只留清 `.bss` |
| `scripts/build_fw.sh` | 除 `fw_itcm.hex` 外再导一份 `fw_dtcm.hex`；新增「.data 结束 < 结果块」检查 |
| `tb/tb_fw_smoke.v` / `tb_fw_fft.v` | 传 `DTCM_FILE("sw/fw/fw_dtcm.hex")` |

**代价（必须记住）**：**两份镜像都要装**。只装 ITCM 的表现是：代码照跑、
结果照出，但所有常量/初值读出来是 X 或 0，**不报任何错**。所以
`build_fw.sh` 会打印两份镜像的用途，TB 头部也写了这句话。

## 复现指纹

```bash
# ① 看符号落在哪 —— 这一步能直接区分「孤儿段」和「端口到不了」
riscv64-unknown-elf-nm -n sw/fw/fw.elf | grep -i ' [dDbB] '
#    常量若出现在 0x2000 以上 → 孤儿段（link.ld 漏段）
#    常量在 0x2000 以下仍是 X  → 端口到不了（核的数据口打不到 ITCM）

# ② 一个常量表 + 一个带初值全局变量，各求和写进 RES，跑 tb_fw_smoke
```

判据：**运行期算出来的内核全对、只有读进来的常量是 X** ⇒ 直接查链接脚本
的小数据段，不要去查核。

## 影响面

- **修之前**：固件只能靠「运行期算出来的数」活着，任何常量表（旋转因子、
  窗、倒数 LUT、SRP 延迟表）都用不了 —— **整条定位链的内核都写不了**。
- **修之后**：FFT 的旋转因子表进 `.data`，随 DTCM 镜像预装，实测逐位可用。
- 老 TB 一个没动、一个没坏（19/19 全绿）。
